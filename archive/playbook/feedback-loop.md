# Feedback and learning loop

The playbook is a set of testable ideas. The goal is to improve viewer experience and production quality, not to prove the initial version right. The owner can change direction at any time.

## 1. Before production: predict

Pick one main hypothesis from [experiments.md](experiments.md), or add one. Write it in the episode brief with a specific intended viewer response, the version being tested, what observation would support or challenge it, and the comparison if one exists. Keep other major choices reasonably stable when comparing episodes; note unavoidable differences. First establish a baseline instead of making up target performance numbers.

## 2. Before publishing: observe and repair

Use [the review checklist](../../templates/review.md). If possible, ask someone unfamiliar with the story to describe the threat, what made the situation unbelievable, the choice and the outcome after one viewing. Record their words, confusion and where it happened without leading them. Also record the owner's feedback, the agent's own review and any unresolved issues separately. If no independent viewer is available, say so: an agent's self-review is useful but is not audience validation.

Fix blocking issues such as incomprehensible plot, missing audio, misleading claims or unresolved rights before delivery/publishing. Retest affected moments after changes. Do not wait for metrics to repair an obvious defect.

For a remake, use two short passages from the exported cut where the viewer should change their mind. Record the first visible clue, the first caption or spoken phrase that gives the answer away, and the character's physical response. Use actual timestamps. If a producer describes an action that is hard to see at phone size, check whether it happens inside the crop, whether it is covered, and whether its result survives the cut. Save a short sequence of frames when it explains the problem. Keep one successful passage as a comparison.

When the owner identifies a distracting movement, find the adjacent frames where it breaks. Compare the replacements at that same moment and at normal speed before carrying the technique through a full episode. Record the owner's judgment separately from the producer's technical checks.

## 3. After publishing: collect consistently

Copy [the performance template](../../templates/performance.md) into the episode folder. If available, collect each platform's native data at approximately 24 hours and 7 days after posting, recording actual observation time and timezone. Use additional checkpoints only when useful. For each platform record views, watch time or average view duration, retention/completion if available, shares, comments and follows/subscribers attributable to the post if available. Capture the retention curve or timestamps of drops/rewatches when the platform exposes them. Log qualitative comments with brief anonymized paraphrases. Never infer that a missing measure equals zero.

Platform metrics have different definitions, reporting windows, audience sizes and eligibility. Compare within the same platform using the same metric, time since publication, video version and a similar format; preserve the native label. Do not directly compare platform view counts or calculate completion from average watch time. Context such as changed length, audience, release time and small sample size can explain apparent differences. Treat early data as provisional and record its limitations.

## 4. Decide and act

Review after each episode, then look across at least three comparable published episodes when available. Three is a practical prompt to review, not a statistically valid threshold. At low volume, favor qualitative observations and describe results as tentative; do not declare a winner or a causal effect from a few posts. For each hypothesis choose **keep**, **revise**, **retest**, or **retire**, explain why, and state the next observable test. If evidence is missing, choose retest or leave pending rather than fabricate a conclusion.

Make an episode-specific correction in its brief/review. Change a playbook rule only when the owner decides or repeated feedback makes a pattern credible; record date, evidence, decision, affected files and next test in [experiments.md](experiments.md). If the data conflicts with creative intent, discuss the tradeoff rather than automatically optimizing for views.

## Example, entirely hypothetical

Hypothesis: showing a strange rule through an action in the opening improves understanding. Test: show the consequence before the explanation in one episode; ask an unfamiliar viewer to describe the rule. Support would be an accurate explanation; confusion would challenge it. Compare with similar prior feedback if available, and note that different stories and small samples prevent a causal claim. No example results or audience data have been collected yet.
